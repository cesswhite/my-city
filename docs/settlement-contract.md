# Shared implementation contract — historical record

> Coordination agreement for the initial implementation. Assignments to “root” and “agents” document that session; they are not current instructions. Some signatures have evolved. Before changing the project, consult the [architecture](architecture.md), [agent guide](agent-guide.md), and current code.

## Ownership and initialization

Colony owns the public members `settlement = Settlement.new()` and `settlement_jobs = SettlementJobs.new()`. Initialization order: Progression, social/daily systems, `Settlement.setup(world, developed)`, then `Jobs.setup(world)`. `Colony.setup(load_existing=true, developed=false)` starts small by default; existing tests explicitly call `setup(false,true)` when they need a developed fixture. A real new game uses `false,false`. A legacy save without settlement data migrates to the developed state. In the original assignment, agents did not edit Colony/Main/Progression; root integrated those changes.

`Settlement.catalog` is `SettlementCatalog.data()`. Persistent `state` contains version, revision, areas (array of IDs), buildings (array of IDs), inhabitants (dictionary mapping ID to `{present, arrived_at, energy, requests}`), projects (ID to `{status, progress}`), nodes (ID to `{period, remaining}`), plots (ID to `{status, planted_at, tended}`), discoveries (array of IDs), jobs (dictionary mapping worker ID to a record), receipts (dictionary mapping receipt ID to a minute), orders (daily counts), sales (daily counts), and serial (integer). Wallet and inventory remain in `Progression.state`; there is no second wallet.

## Settlement methods

- `is_present(id)`, `area_open(id)`, `building_ready(id)`, `snapshot()`, and `restore(data)` (validated before loading); `view()` returns duplicate state plus catalog geometry.
- `task_spec(task_id, worker="player")` returns `{id, kind, title, room, at:[x,y], minutes, energy, inputs:{}, outputs:{}, ...}` or `{}`. IDs: `gather:node`, `produce:recipe`, `build:project`, `explore:mission`, `plant:plot`, `tend:plot`, `harvest:plot`.
- `offer(task_id, worker="player")` returns `{ok,message,spec}`. It is pure and checks prerequisites, stocks, resources, areas, and active residents. It does not check willingness or whether the worker is busy; Jobs does that. Planning does not require proximity.
- `tasks(worker="player")` returns an array of specifications with `ok,message` for unlocked/known tasks, not all future content.
- `prepare_task(task_id,worker)` checks the offer, returns `{ok,message,spec,escrow:{}}`, and consumes production/planting inputs or a project's initial costs once. Jobs must check willingness and busy status before preparation.
- `complete_task(job)` grants idempotent results for `job.id`. It requires the physical target, or the return board for NPC gathering/exploration. A job with `phase="returning"` is allowed at the board only when `progress>=required` and `worked=true`. Returns `{ok,message}`; handles node stock reserved during preparation, project progress completion, discovery, and arrivals. Jobs is responsible for energy.
- `cancel_task(job)` returns escrow and reserved stock while preserving invested project costs/progress. `note_event(worker,text,kind="trabajo")` records only the actor and actual nearby witnesses, without global omniscience. The Spanish `trabajo` identifier remains part of the API.
- `project_status(id)` returns `{id,title,status,progress,minutes,cost,ok,message,area,at,requires,discovery,arrival}`; `stage()` returns `{index,title,next}`; `market()` returns rows `{id,name,price,remaining,owned}`; `sell(id,quantity)` validates shop proximity and quota; `orders()` returns rows `{id,title,requester,items,coins,ok,message}`; `deliver_order(id)` validates actual requester proximity, inventory, and limits; `context_for(id)` returns a small public/personal summary.

## Jobs API and persistence

The Jobs API is `setup(world)`, `request(worker,task_id)` → `{ok,message}`, `preview(worker,task_id)` → `{ok,message}`, `cancel(worker)` → result, `tick(elapsed_minutes=5.0)`, `busy(id)`, and `daily_state(id)` → current visible task or `{}`. `autonomous_offer(id)` returns an eligible task ID or `""`. In the original integration, root called the Jobs tick before routines and DailyLife and skipped busy residents in routines; the assigned agent made DailyLife skip busy IDs. Conversation and sleep pause physical progress; jobs must not progress while moving, held, or asleep. Jobs must move through the existing `world.travel_to(id,room,at)` signature, which must be inspected. A player request walks to the site and performs work; manual movement cancels through Main. NPCs return to the community board with gathered goods or exploration results before committing them.

The minimum persistent job schema is `{id:String,worker:String,task_id:String,kind:String,target_room:String,target:Array,phase:String [travelling/working/returning/paused],progress:float,required:float,started:int,escrow:Dictionary,worked:bool,energy:float}`. Optional documented fields are allowed if the validator is updated. The work target is the immutable catalog specification; the return destination is `catalog.board`. Project progress is shared in `state.projects`. Only one actor may use the same node, plot, or project at a time; the original root-owned offer check enforces this through jobs. NPC work energy lives in `state.inhabitants[id].energy` (0–100), with recovery when not working/asleep. Refusal-insistence state lives in `inhabitants[id].requests`; relationship consequences apply only to repetition of the same request. Use `world.relationship_for(id,"player")`. The optional `work_profile` field in `residents.json` defines work profiles; preserve merging it from the catalog when loading saves.

## World integration

`world.home_project_state()` (Main) adds a `settlement` state snapshot. Sprite and interaction adapters read `state.settlement`. The pure `SettlementWorld` module may use the catalog. Do not mutate caches. Plot geometry is fixed; gates here are only visual/hit targets, while root integrates route gates in Colony. Root calls `SettlementWorld` action matching from Main as needed; the assigned agent reports the API. Filter unavailable façades, doors, lights, and smoke; extend Layout with a forest area and static plot footprints. Change only geometry and `at` coordinates in `settlement.json` if needed; the original root assignment avoids concurrent edits to that data. Job `at` positions must be walkable according to Navigation.

## UI

The new `SettlementUI(host)` exposes `show_overview(tab="town")`, `show_task(task_id)`, `show_person(id)`, `show_market()`, `close()`, and `panel:Control`; it uses existing host overlays and modal layout. Root initializes `settlement_ui`, connects close/resize/modal-input handling, and adds `begin_settlement_task(task_id,worker="player")`. That method calls `Jobs.request` and closes the UI on success. Verify the existing `host.show_world_notice(text)` signature. The Journal adds clear **Pueblo / Aprendizajes** (Town / Apprenticeships) navigation to reach the Town UI; the permanent toolbar does not change. The UI uses the `Colony.settlement` and `settlement_jobs` APIs above. Show locked requirements, current work/cancellation, resources, projects, and volunteers. Keep the UI scrollable, readable, and keyboard-focusable. The assigned agent may choose richer internal UI methods but must report the hooks required by root.

## Backend

Add optional bounded settlement context and one controlled action, `colaborar`; the engine selects `settlement_jobs.autonomous_offer(id)` and calls `request`. AI cannot specify rewards, costs, targets, or unlock state. Derive backend identities from the versioned resident JSON through a build import if runtime-compatible. Root caps perception at five and supports `colaborar`.
